## 0. 一句话定义

为连锁餐饮企业构建一套「**门店端一键订货 + 总部端智能补货**」的 Web 系统：把店长凭经验拍脑袋的订货动作，替换为基于历史消耗、星期规律、在途库存与安全库存的**建议订货量**，并配套审批、收货入库、效期预警与周转分析，最终降低缺货率与过期损耗。

## 2. 系统目标

### 2.1 业务背景（用于报告 1.1）

连锁餐饮门店的原料订货普遍依赖店长经验：订多了 → 生鲜过期报损、占用现金流；订少了 → 高峰期断货、被迫就近溢价采购。总部缺乏对各门店库存与订货的实时可见性，跨店调拨靠电话协调，损耗数据无法归因。原料还存在"箱 / 千克 / 克"多级单位与配方折算问题，人工核算极易出错。

### 2.2 目标（可度量，用于报告 1.2）

| 编号 | 目标 | 度量口径 |
|---|---|---|
| G1 | 订货决策从经验驱动转为数据驱动 | 系统能对 ≥90% 的常备 SKU 自动生成建议订货量，并给出计算依据 |
| G2 | 库存全流程可追溯 | 每一次库存变动（入库/出库/盘点/报损/调拨）都有单据与操作人，账面可回溯 |
| G3 | 缺货与损耗可预警 | 断货风险、临期、滞销三类预警在业务发生前 T-1 天触发 |
| G4 | 订货流程规范化 | 订货单全生命周期状态可查，异常订货（偏离建议量 >50% 或金额超阈值）强制走审批 |
| G5 | 总部具备决策视图 | 提供门店缺货率、库存周转天数、损耗率、订货达成率四类指标看板 |

### 2.3 范围边界

**做（P0/P1）**：门店订货全流程、库存出入库与批次效期、补货建议算法、审批流、预警与看板、主数据与权限。

**不做（明确写入报告，避免被追问）**：真实 POS/ERP/供应商系统对接（以 CSV 导入 + 模拟接口替代）、真实支付与结算、冷链温控 IoT、多语言、多币种、完整财务对账。

## 5. 数据与业务逻辑要点

### 5.1 核心实体（初版，设计阶段细化）

| 域 | 实体 | 关键字段（示意） |
|---|---|---|
| 组织 | `store` / `region` | 门店-区域-总部三级 |
| 商品 | `product` / `category` | SKU 编码、名称、**库存单位**、订货单位、保质期天数、存储条件 |
| 单位 | `unit_conversion` | product_id, from_unit, to_unit, factor |
| 配方 | `recipe` / `recipe_item` | 菜品 → 原料及用量（用于销量折算消耗） |
| 策略 | `replenishment_policy` | 门店+SKU 维度：安全库存、提前期、订货周期、MOQ、订货包装倍数、最大库存 |
| 库存 | `stock` | 门店+SKU 的可用量、锁定量、在途量 |
| 库存 | `stock_batch` | 批次号、生产日期、到期日、数量（FEFO 依据） |
| 流水 | `stock_movement` | 类型（IN/OUT/ADJUST/LOSS/TRANSFER）、数量、单据号、操作人、时间 |
| 消耗 | `sales_daily` | 门店+日期+菜品销量 |
| 消耗 | `consumption_daily` | 门店+日期+SKU 实际耗用量（由销量折算或出库汇总） |
| 订货 | `purchase_order` / `purchase_order_item` | 单号、状态、建议量 vs 实订量、金额、到货差异 |
| 审批 | `approval_record` | 单据、审批人、结论、意见、时间 |
| 预警 | `alert` | 类型、级别、对象、触发时间、处理状态 |

### 5.2 关键业务规则（设计中逐条落到类方法上）

| 编号 | 规则 | 设计意图 |
|---|---|---|
| BR-01 | **库存统一以最小计量单位存储**（克/毫升/个），展示与订货时按换算系数转换 | 避免小数精度丢失与多级单位混乱，是本系统最重要的设计决策 |
| BR-02 | 可用库存 = 现存 − 锁定量；订货可参考量还需叠加在途量 | 防止重复订货 |
| BR-03 | 出库默认 **FEFO**（先到期先出），同效期按入库时间 FIFO | 控制损耗，餐饮刚需 |
| BR-04 | 所有库存变动必须生成 `stock_movement`，且在同一事务内更新 `stock` | 保证账实可追溯、可重算 |
| BR-05 | 库存扣减使用乐观锁（version）或行锁，冲突时重试并返回明确提示 | 并发安全，是"可靠性"得分点 |
| BR-06 | 订货单状态机：`DRAFT → SUBMITTED → APPROVED/REJECTED → CONFIRMED → RECEIVED → CLOSED`，另有 `CANCELLED` | 非法跳转必须被状态机拒绝，需写单测 |
| BR-07 | 触发审批条件：订单金额 > 阈值（默认 500 元）**或** 实订量偏离建议量 > 50% **或** 订货量超过最大库存 | 把管理规则固化为代码 |
| BR-08 | 到货实收 ≠ 应收时，按**实收**入库，差异写入 `purchase_order_item` 并置订单为「差异待处理」 | 覆盖异常流，用例文档必备 |
| BR-09 | 报损必须选择原因分类（过期/变质/破损/加工损耗），并计入损耗率 | 支撑损耗归因分析 |
| BR-10 | 临期预警阈值按 SKU 保质期比例配置（默认剩余 30% 保质期时预警） | 可配置，体现设计弹性 |

### 5.3 补货算法设计（系统"智能"部分，需在报告 4.x 单独成节）

**输入**：近 8 周每日消耗、SKU 补货策略、当前库存与在途、促销/节假日日历。

1. **基线需求**
   `d̄ = 近 N 天（默认 28）有效消耗总和 / 有效天数`（剔除闭店日与异常零值）

2. **星期因子**（餐饮强周期）
   `w_dow = 该星期几平均消耗 / 全期平均消耗`，取近 8 周平滑

3. **趋势修正**（Holt 线性趋势或简单线性回归斜率，取近 28 天）
   `base_t = d̄ × (1 + trend × t)`

4. **日预测**：`f_t = base_t × w_dow × promo_factor × holiday_factor`

5. **提前期需求与安全库存**
   - `μ_L = Σ f_t`（t 覆盖提前期 L 天）
   - `σ_L = 提前期内消耗标准差`
   - `SS = Z × σ_L`（服务水平 95% → Z=1.65，可按 SKU 配置）

6. **补货点**：`ROP = μ_L + SS`，当可用库存 < ROP 时进入建议订货清单

7. **建议订货量**
   `Q_raw = 覆盖期需求(L + 订货周期) + SS − 可用库存 − 在途`
   `Q = max(0, ceil(Q_raw / 订货包装倍数) × 订货包装倍数)`，且 `Q ≥ MOQ`，`Q ≤ 最大库存 − 可用 − 在途`

8. **冷启动降级**：数据不足 14 天的 SKU 退化为「近 7 天日均 × 覆盖天数」；无数据则提示人工设置最低库存。

9. **可解释输出**（关键加分项）：返回结构化明细而非单一数字——
   ```json
   { "sku": "SKU001", "suggestQty": 11, "unit": "箱",
     "detail": { "onHand": 12, "inTransit": 0, "locked": 1,
                 "forecastDemand": 20, "safetyStock": 4, "rop": 18 },
     "reason": "可用库存 11 箱低于补货点 18 箱，覆盖至下次到货预计需 20 箱" }
   ```

**验证方式**：用 seed 数据做回测（历史 90 天），对比"系统建议"与"实际发生"的缺货次数与库存持有量，输出对比表——这一数据可直接支撑报告 6.4 的结论。

```
 Service 层     ── 业务用例实现（订货、库存、补货、审批）
   ├─ 领域服务：InventoryService / ReplenishmentService / ApprovalService
   └─ 算法模块：ForecastEngine（可独立单测）
        │
 Repository 层  ── MyBatis-Plus / JPA
        ▼
 MySQL 8（+ Redis 可选：会话、预警缓存）
        ▲
 定时任务（Spring Scheduler / XXL-Job 简化版）：补货计算、预警扫描
```

## 9. 分阶段实施步骤

按 6 周（约 30 个工作日）排期，若课程周期不同可按比例伸缩；每个阶段都有**可检查的产出物**，避免"最后一周才写文档"。

### 阶段 0｜启动与基座（W1 前半，2 天）
- 建仓、配置 `.devcontainer` 与 `docker-compose`（MySQL + 空后端 + 空前端，先保证能起来）
- 确立术语表（SKU、补货点、安全库存、提前期、FEFO、MOQ、到货差异…）
- 分工确认、分支规范、看板（GitHub Projects）建好
- **产出**：仓库可一键启动的空壳 + 分工表

### 阶段 1｜业务分析与建模（W1 后半，3 天）
- 业务背景、目标、干系人清单；业务用例图
- P1–P5 五张核心业务活动图（含泳道：门店 / 区域 / 中央厨房 / 系统）
- 撰写《01 业务分析说明书》
- **产出**：D1 初稿 + 活动图源文件

### 阶段 2｜需求分析与建模（W2，5 天）
- 识别参与者、系统用例图（并做 include/extend 重构）
- 逐份编写 15 份用例文档（重点写异常流：库存不足、审批驳回、到货短缺、并发冲突、效期已过禁收）
- 非功能需求（性能、可靠性、安全、易用性）量化描述
- **产出**：D2 初稿

### 阶段 3｜系统分析与设计（W3，5 天）
- 架构图（分层 + 模块依赖）
- 按用例做交互分析：≥10 张顺序图 → 归纳设计类图 → 补全校验类/边界类

- **产出**：D3、D4 初稿 + `docs/uml/` 全套源文件

### 阶段 4｜迭代一：打通骨架与库存（W4，7 天）
- 登录鉴权、RBAC 与数据权限拦截
- M1 主数据 CRUD（商品、门店、单位换算、策略配置）

- **产出**：可登录 → 能建商品 → 能入库出库 → 库存准确变化的**可演示版本 v0.1**

### 阶段 5｜迭代二：智能补货与订货主线（W5，8 天）
- ForecastEngine：星期因子 + 趋势 + 安全库存 + 建议量 + 可解释明细；单测覆盖边界（零消耗、新品、超长提前期）

### 阶段 6｜迭代三：预警、看板与收尾功能（W6 前半，4 天）
